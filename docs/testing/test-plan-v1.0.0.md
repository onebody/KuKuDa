## 1. 测试概述

### 1.1 测试目标

根据项目质量保障计划，本次测试的目标为：

- **功能覆盖率**：100%（所有节点类型、所有数据流场景）
- **测试用例通过率**：≥ 95%
- **Bug 修复时间**：严重 Bug 24 小时内修复，一般 Bug 3 个工作日内修复
- **性能达标率**：100%（10 个节点工作流执行时间 < 5 秒）
- **文档完整率**：100%（用户文档、开发文档、部署文档）

### 1.2 测试对象

KuKuDa 节点架构改造项目，包括：
- 前端：React + TypeScript + Zustand + React Flow
- 后端：Express + Prisma + PostgreSQL + MinIO
- 实时通信：Socket.io (WebSocket)

### 1.3 测试依据

- 产品需求文档 (PRD v1.0.0)
- 架构设计文档 v1.0.0
- 项目计划 v1.0.0
- 相关技术标准与规范

## 2. 测试范围

### 2.1 功能测试范围

#### 2.1.1 节点类型测试（8 种节点）

**源节点（5 种）**：
1. **文本输入节点（TextInputNode）**
   - 文本输入/编辑功能
   - 多行文本支持
   - 清空功能

2. **单图片输入节点（SingleImageInputNode）**
   - 单张图片上传
   - 图片预览
   - 图片删除
   - 拖拽上传
   - Ctrl+V 粘贴上传

3. **多图片输入节点（MultiImageInputNode）**
   - 批量图片上传（最多 20 张）
   - 自动编号（1-20）
   - 批量预览
   - 单个/批量删除
   - 清空功能

4. **单文件输入节点（SingleFileInputNode）**
   - 单个文件上传
   - 文件信息显示
   - 文件删除

5. **多文件输入节点（MultiFileInputNode）**
   - 批量文件上传（最多 50 个）
   - 文件列表显示
   - 单个/批量删除

**处理节点（3 种）**：
1. **AI 绘图节点（AIImageNode）**
   - Prompt 输入
   - AI 绘图接口调用
   - 生成图片预览
   - 生成历史记录

2. **文本输出节点（TextOutputNode）**
   - 上游文本读取
   - 文本显示
   - 文本复制

3. **技能节点（SkillNode）**
   - 技能选择
   - 动态表单生成
   - 技能接口调用
   - 结果展示

#### 2.1.2 数据流动测试

1. **被动读取逻辑**
   - 处理节点不主动触发上游执行
   - 上游数据变化时自动更新

2. **等待状态**
   - 上游无输出时显示"等待上游数据..."
   - 黄色边框标识
   - Tooltip 提示

3. **输入合并策略**
   - 文本合并（换行符拼接）
   - 图片/文件 URL 合并（数组合并）
   - 多种类型合并（按类型分别处理）
   - 合并冲突处理

#### 2.1.3 文件上传测试

1. **后端接口**
   - 单文件上传接口（POST /api/upload/single）
   - 批量文件上传接口（POST /api/upload/batch）
   - 文件删除接口
   - MinIO 集成

2. **前端 UI**
   - 单图片选择弹窗
   - 批量图片上传弹窗
   - 图片预览网格
   - 单文件选择弹窗
   - 多文件选择弹窗

#### 2.1.4 AI 功能测试

1. **AI 绘图接口对接**
   - 后端 AI 绘图接口代理
   - AI 服务选型与测试
   - 前端 AI 绘图节点完整功能

2. **技能节点接口对接**
   - 技能管理后端接口
   - 技能节点配置弹窗
   - 技能接口调用与结果处理

#### 2.1.5 执行状态测试

1. **等待状态**：黄色边框 + "等待上游数据..."
2. **执行中状态**：蓝色边框 + 进度条/动画
3. **成功状态**：绿色边框 + "✓ 执行成功" + 显示结果
4. **失败状态**：红色边框 + "✗ 执行失败" + 错误信息 Tooltip

#### 2.1.6 React Flow 画布交互测试

1. 节点拖拽、连接、删除功能
2. 节点句柄样式与连接线样式定制
3. 画布缩放、平移、迷你地图

#### 2.1.7 WebSocket 实时通信测试

1. 后端 WebSocket 服务（Socket.io）
2. 前端 WebSocket 集成（节点状态实时更新）
3. 执行状态推送（node:status-change、workflow:complete）

### 2.2 性能测试范围

1. **工作流执行速度**：10 个节点工作流执行时间 < 5 秒
2. **大数据量传递性能**：20 张图片 URL 数组传递
3. **复杂工作流布局计算性能**：50+ 节点
4. **页面加载时间**：< 2 秒
5. **API 接口响应时间**：< 500ms

### 2.3 安全测试范围

1. **文件上传漏洞**：恶意文件、超大文件
2. **API Key 泄露**：前端不直接调用 AI 接口
3. **SQL 注入、XSS 等常见漏洞**
4. **文件类型限制**：图片只允许 jpg、png 等
5. **文件大小限制**：图片最大 10MB，文件最大 100MB

### 2.4 兼容性测试范围

1. **浏览器兼容**：Chrome、Firefox、Safari、Edge
2. **操作系统兼容**：Windows、macOS、Linux
3. **屏幕尺寸适配**：桌面端（1920×1080、1366×768）

### 2.5 不在测试范围

1. **单元测试**：由开发人员（柏码）负责，目标覆盖率 ≥ 60%
2. **用户验收测试**：由产品经理（茗需）负责
3. **AI 服务商的稳定性测试**：依赖第三方服务，只测试接口调用逻辑

## 4. 测试方法

### 4.1 功能测试方法

#### 4.1.1 等价类划分

**适用场景**：输入有取值范围的字段

**示例**：
- **文件上传数量**：
  - 有效等价类：1-20 张图片（多图片输入节点）
  - 无效等价类：0 张、21 张
- **文件大小**：
  - 有效等价类：1MB-10MB（图片）、1MB-100MB（文件）
  - 无效等价类：0MB、11MB（图片）、101MB（文件）

#### 4.1.2 边界值分析

**适用场景**：边界容易出错

**示例**：
- **文件上传数量边界**：0, 1, 19, 20, 21（多图片输入节点）
- **文件大小边界**：0MB, 1MB, 9.9MB, 10MB, 10.1MB（图片）

#### 4.1.3 场景法

**适用场景**：业务流程测试

**示例**：
- **用户下单流程**（类比工作流执行流程）：
  1. 创建文本输入节点
  2. 创建 AI 绘图节点
  3. 连接两个节点
  4. 在文本输入节点中输入 Prompt
  5. 执行工作流
  6. 查看 AI 绘图节点输出

#### 4.1.4 状态转换法

**适用场景**：状态机测试

**示例**：
- **节点执行状态转换**：
  - 等待 → 执行中 → 成功
  - 等待 → 执行中 → 失败
  - 成功 → 等待（上游数据变化）

#### 4.1.5 错误推测法

**适用场景**：基于经验推测易错点

**示例**：
- 文件名包含特殊字符
- 网络中断
- 并发操作
- 浏览器兼容性问题和异常场景

### 4.2 性能测试方法

#### 4.2.1 负载测试

**目标**：验证系统在正常负载下的性能

**方法**：
1. 模拟 10 个节点工作流执行
2. 测量执行时间
3. 目标：执行时间 < 5 秒

#### 4.2.2 压力测试

**目标**：验证系统在极端负载下的稳定性

**方法**：
1. 模拟 50+ 节点工作流
2. 模拟 20 张图片 URL 数组传递
3. 监控内存占用、CPU 使用率

#### 4.2.3 并发测试

**目标**：验证系统在高并发下的性能

**方法**：
1. 模拟多个用户同时执行工作流
2. 监控响应时间、吞吐量

### 4.3 安全测试方法

#### 4.3.1 漏洞扫描

**工具**：OWASP ZAP

**方法**：
1. 自动扫描常见漏洞（SQL 注入、XSS、CSRF 等）
2. 手动验证扫描结果

#### 4.3.2 代码审查

**方法**：
1. 审查文件上传逻辑（文件类型、大小限制）
2. 审查 API Key 存储和调用逻辑
3. 审查 SQL 查询逻辑（防止 SQL 注入）

#### 4.3.3 渗透测试

**方法**：
1. 模拟恶意文件上传
2. 模拟超大文件上传
3. 模拟 API Key 窃取

| **性能效率** | 工作流执行时间 | 10 节点 < 5 秒 | 性能测试 |

| **性能效率** | API 接口响应时间 | < 500ms | 性能测试 |

| 标准 | 验收方法 |
|------|----------|
| 1. 所有功能符合 PRD 和架构设计 | 功能测试 |
| 2. UI 符合设计规范 | UI 走查 |
| 3. 接口符合接口定义 | 接口测试 |

#### 7.2.2 性能质量

| 标准 | 验收方法 |

### 7.3 发布标准

**必须满足条件**：

1. ✅ 功能覆盖率 = 100%
2. ✅ 测试用例通过率 ≥ 95%
3. ✅ 无严重 Bug（Critical、Major）
4. ✅ 性能达标率 = 100%（10 个节点工作流执行时间 < 5 秒）
5. ✅ 无高危安全漏洞
6. ✅ 文档完整率 = 100%（用户文档、开发文档、部署文档）

**有条件发布**（需审批）：

1. ⚠️ 测试用例通过率 90%-95%，但无严重 Bug
2. ⚠️ 存在 Minor 级别的 Bug，但不影响核心功能
3. ⚠️ 性能未完全达标，但可通过后续优化解决

**禁止发布**：

1. ❌ 功能覆盖率 < 100%
2. ❌ 测试用例通过率 < 90%
3. ❌ 存在严重 Bug（Critical、Major）
4. ❌ 存在高危安全漏洞

### 8.3 风险应对措施

#### 8.3.1 测试时间不足

**应对措施**：
1. **优先级排序**：优先测试核心功能（节点类型、数据流动）
2. **自动化测试**：编写自动化测试脚本，提高测试效率
3. **测试左移**：前期测试介入，尽早发现缺陷
4. **缓冲时间**：使用项目缓冲时间（8 人天）

#### 8.3.2 缺陷修复不及时

**应对措施**：
1. **缺陷优先级**：严重 Bug 24 小时内修复，一般 Bug 3 个工作日内修复
2. **每日跟踪**：每日站会跟踪缺陷修复进度
3. **资源协调**：必要时协调开发人员优先修复缺陷
4. **缓冲时间**：使用项目缓冲时间（8 人天）

#### 8.3.3 测试环境不稳定

**应对措施**：
1. **独立环境**：搭建独立稳定测试环境，与生产环境隔离
2. **配置文档化**：环境配置文档化，便于快速重建
3. **定期检查**：定期检查环境状态，及时发现和解决问题
4. **备份恢复**：环境配置备份，快速恢复

#### 8.3.4 测试数据准备不足

**应对措施**：
1. **提前准备**：提前准备测试数据，建立测试数据清单
2. **自动化生成**：编写脚本自动化生成测试数据
3. **真实数据**：使用真实数据（脱敏后）进行测试
4. **数据管理**：测试数据版本管理，便于复用

## 9. 缺陷管理

### 9.1 缺陷生命周期

```
新建（New） → 打开（Open） → 修复（Fixed） → 验证（Verified） → 关闭（Closed）
                     ↓
                拒绝（Rejected）
                     ↓
                重新打开（Reopened）
```

### 9.2 缺陷严重性分级

| 级别 | 描述 | 示例 | 修复时间 |
|------|------|------|----------|
| **Critical（致命）** | 系统崩溃、数据丢失、安全漏洞 | 系统崩溃、文件上传漏洞 | 24 小时内 |
| **Major（严重）** | 核心功能不可用、主要功能错误 | AI 绘图功能不可用、数据流动错误 | 3 个工作日内 |
| **Minor（一般）** | 边缘功能错误、UI 问题 | 图片预览显示异常、Tooltip 文字错误 | 7 个工作日内 |
| **Trivial（轻微）** | 文案错误、易用性问题 | 按钮文字错误、提示信息不清晰 | 下个版本修复 |

### 9.3 缺陷优先级

| 优先级 | 描述 | 示例 |
|--------|------|------|
| **高** | 必须立即修复 | 系统崩溃、安全漏洞 |
| **中** | 应在下个版本前修复 | 核心功能错误 |
| **低** | 可以延后修复 | UI 问题、文案错误 |

### 9.4 缺陷报告格式

```markdown
## 缺陷报告 #[ID]

**标题**：[模块] [简短描述]
**发现日期**：YYYY-MM-DD
**发现人**：[姓名]
**严重性**：Critical/Major/Minor/Trivial
**优先级**：高/中/低
**状态**：New/Open/Fixed/Closed/Reopened
**模块**：[模块名称]
**版本**：[发现版本]
**重现步骤**：
1. [步骤1]
2. [步骤2]
3. [步骤3]
**预期结果**：[...]
**实际结果**：[...]
**附件**：[截图、日志、录屏等]
**备注**：[其他相关信息]
```

### 9.5 缺陷跟踪工具

**工具**：GitHub Issues

**使用方式**：
1. 新建 Issue，标签设置为 `bug`
2. 填写缺陷报告（按模板）
3. 分配责任人（Assignee）
4. 设置优先级（Priority）和严重性（Severity）
5. 跟踪缺陷状态变化
6. 验证修复后关闭缺陷
